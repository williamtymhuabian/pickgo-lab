# PickGo Lab：通用移动抓取机器人设计草案 v0.1

日期：2026-10-16。依据：本目录提取包中的主控制代码与用户确认的“底盘＋机械臂”目标。

这是后续实体机器人方案，尚未采购或做硬件验证。下文尺寸、载荷和验收门槛是建议目标，不是已测性能。预算、取物高度、物体大小和重量仍待确认。当前已实现轻量运动仿真、原视觉函数适配及共享的 Python/HTTP/MCP 入口，实际使用以 README 和 docs/mcp.md 为准。

## 1. 先定义要造出来的机器人

第一版任务：在室内平地，从固定低台上的指定轻小物体中识别目标，抓起后运输到另一固定低台或收纳盒，放下并报告结果。取物台与放物台高度须落在机械臂装车后的实际工作空间内。

建议测试物体：30–100 g 的积木或小盒，表面不透明、不反光、易夹持。先做单物体，再做颜色分类。重量目标须加上夹爪、相机、安装件的重量重新核算机械臂负载与关节扭矩。

第一版使用“移动—停稳—操作—收拢—移动”。底盘和机械臂不同时主动运动。不把开门、爬楼、抓透明物体、杂乱堆叠、多机器人调度列入首版验收。

“通用”的含义是：任务和技能接口可以复用；更换硬件时替换驱动、模型、限位、标定和参数。可达空间、精度、负载和自由度始终取决于实体设备，不能靠统一接口自动获得。

## 2. 分层与职责

### 应用层：你向机器人提出什么任务

网页控制台、命令行或未来的语音入口提交结构化任务，例如“把取物台 A 的红色方块送到盒 B”。界面可查看任务阶段、相机画面、机器人状态、故障和取消结果。语音或语言模型仅产生受校验的任务描述，不直接发布电机指令。

### 任务层：这一件事如何完成

一个任务执行器组合 navigate、dock、observe、pick、stow、place 等技能，保存进度、资源占用和可恢复状态。首版采用显式有限状态机；流程分支明显增多后再考虑行为树。

### 技能层：把可靠动作封成模块

- navigate_to：抵达工位附近，返回定位与误差状态。
- dock_to_station：利用工位标记/视觉做末端对位，并验证停车位置满足机械臂可达性。
- observe：输出目标标识、位姿、尺寸、置信度、时间戳和坐标系。
- pick：选择可执行的抓取姿态，预抓、接近、闭爪、验证、抬升。
- place：到达预放位，受控接近、松爪、验证释放、退出。
- stow：进入经验证的运输位或安全待机位。
- transport：确认物体固定、机械臂收拢后执行低速搬运；优先使用车载托盘固定物体。

每个技能声明前置条件、资源、超时、反馈、后置条件和失败策略。反馈不足时返回 UNKNOWN 或 UNSUPPORTED，不把“命令已发送”当作“动作已完成”。

### 能力层：对硬件的统一要求

Base、Arm、Gripper、Camera、Detector、Localization 六类接口，另配 SafetySupervisor、CalibrationStore 和 RobotStateStore。能力注册表记录哪些接口受支持，以及位姿约束、工作空间和反馈能力。

例如小型四自由度机械臂只声明平面位置和受约束的夹爪朝向；要求任意六维姿态的任务在规划前就拒绝。首选带位置反馈的五/六自由度机械臂，任务若需要任意夹爪朝向则选六自由度且验证奇异位形与可达空间。

### 驱动层：实际如何与设备通信

现有设备：Fairino RPC、串口夹爪、Woosh SDK/WebSocket、ROS 相机。

自建小机器人：机械臂串口/CAN/USB驱动、编码器底盘控制板、夹爪驱动、RGB-D相机。任务层不读取设备 IP、串口号或厂家数据包。

### 独立停止链

硬件急停与控制板看门狗直接作用于执行机构；软件监督器处理互锁、状态过期、命令超时和模式仲裁。两者职责独立。取消任务、软件停止、硬件急停不是同一种操作，也不能互相替代。

## 3. 一次完整搬运如何执行

1. PRECHECK：设备在线、标定有效、状态新鲜、急停已复位、任务参数和能力满足要求。
2. STOW：空载进入运输位并确认完成。
3. NAVIGATE_PICK：底盘去取物工位附近。
4. DOCK_PICK：工位视觉对位；验证连续一段时间速度接近零且底盘保持停止。
5. OBSERVE：采集时间匹配的 RGB-D，识别目标并转换到机械臂基座坐标。
6. PLAN_PICK：检查工作空间、抓取朝向、碰撞、载荷和稳定性；生成预抓取与接近路径。
7. PICK：张爪、接近、闭爪，利用夹爪位置/电流/力或二次视觉判断是否持物。
8. SECURE：优先把物体转移到车载托盘并确认固定，再收拢；若采用夹爪持物运输，必须验证掉电保持、惯性和稳定性，并使用专门运输姿态。
9. NAVIGATE_DROP：允许底盘移动，去投放工位。
10. DOCK_DROP：停车对位；若托盘运输，则在固定车载坐标重新抓起物体。
11. PLACE：规划到预放位、下降、释放、验证、退出。
12. STOW_AND_FINISH：机械臂收拢，核验任务后置条件，记录结果。

任意阶段取消：停止发新运动指令，发出受控停止请求，等待实际停止反馈；停止确认超时则升级故障，不能立即宣称 CANCELED。故障时保留“是否持物”的状态；不要无条件松爪或在环境未知时自动回零。

物体未发现：有限次重新观测。停车误差超限：有限次重新对位。抓取失败：先检查物体与夹爪状态，再决定是否重试。通信中断或动作结果未知：进入人工确认/状态核验，不盲目重发闭爪、进给或导航命令。

## 4. 统一接口与数据约定

内部使用 SI：米、弧度、秒、米/秒。Pose 使用带 frame_id 和 timestamp 的位置＋四元数，深度数据保留 encoding、单位、内参及时间戳。厂家毫米/角度制只在适配器边界转换。

外部 REST 是应用入口，内部 ROS 2 Action 承载长时任务，Topic 承载传感器/连续状态，Service 用于短时查询和配置。不是让每个硬件都包一层 HTTP。

建议接口（项目自定义契约，不是已存在的 SDK）：

```text
POST /api/v1/tasks                 -> 202 + task_id（接收，不代表成功）
GET  /api/v1/tasks/{task_id}       -> 状态、当前步骤、反馈、错误、证据
POST /api/v1/tasks/{task_id}/cancel -> 取消请求已接收；随后核验是否停稳
GET  /api/v1/robot/state           -> 设备状态、时间戳、模式、持物状态
GET  /api/v1/robot/capabilities    -> 受支持动作、约束、反馈能力

Base.navigate(goal) / stop() / state()
Arm.move_joints(goal) / move_pose(goal) / execute_trajectory(plan) / stop() / state()
Gripper.open() / close(command) / state()
Camera.capture_synced() -> RGB、Depth、CameraInfo、时间戳
Detector.detect(frame, query) -> 目标集合、置信度、位姿估计及坐标系
```

每个后端只实现实际支持的方法；不支持轨迹执行或关节反馈时显式报告。技能根据能力选路径，不能用 MoveCart 假装实现完整轨迹控制。

任务示例：

```json
{
  "request_id": "user-generated-unique-id",
  "type": "pick_and_deliver",
  "object": {"class": "block", "color": "red"},
  "source": {"station_id": "pickup_A"},
  "destination": {"station_id": "bin_B"},
  "policy": {"max_observe_retries": 2, "transport_mode": "tray"}
}
```

任务状态：QUEUED、RUNNING、CANCELING、SUCCEEDED、FAILED、CANCELED、NEEDS_ATTENTION。持物状态独立为 EMPTY、HOLDING、SECURED_IN_TRAY、UNKNOWN。

request_id 用于幂等接收；一个执行器是运动指令的唯一写入者。Base/Arm/Gripper 有资源锁，遥控与自动模式有显式仲裁。应用崩溃后将未完成运动标为待核验；从日志恢复业务进度不等于恢复机械动作。

统一错误至少包括 NOT_READY、UNSUPPORTED、STALE_STATE、TARGET_NOT_FOUND、INVALID_DEPTH、OUT_OF_REACH、PLAN_FAILED、GRASP_FAILED、TIMEOUT、DRIVER_ERROR、STOP_UNCONFIRMED。

每次任务保存 robot_id、profile版本、标定版本、目标位姿、关键帧、驱动反馈、步骤起止时间与失败原因。

## 5. 坐标与感知是最关键的迁移点

目标坐标链：map → odom → base_link → arm_base_link → arm joints → tool0 → gripper_tcp。导航传感器挂在 base_link；腕部相机挂在 tool0；固定相机则挂在对应刚性结构上。camera_optical_frame 使用相机光学坐标约定，不复用机械臂坐标轴定义。

现有 robot.py 的 map → robot_base 是固定单位变换，不能当作移动机器人的真实定位。新系统用定位输出 map → odom，用里程计输出 odom → base_link；机械臂安装变换用实测外参。每条 TF 只由一个节点发布。

最低标定清单：轮径/轮距、相机内参和深度尺度、相机到机械臂/工具外参、机械臂到底盘安装外参、夹爪 TCP、关节零位、取放工位参考。使用图像采集时刻的变换；状态或变换过期就拒绝执行。

现有“像素差直接乘比例移动”只作为原工位兼容策略。通用策略使用相机内参、有效深度和外参把像素反投影到三维，并进行目标区域深度滤波、无效值剔除与时间同步。单点深度不作为可靠抓取距离。

有深度相机时优先实现 RGB-D 平面抓取。只有普通相机时，必须引入已知平面/标记与标定，只能支持被明确约束的任务；不能把二维检测框当成完整六维抓取姿态。

首版让底盘到粗定位区域，再利用取物台的视觉标记精定位。地图导航抵达成功不代表抓取坐标准确。标记能帮助对位，但仍需标定、可见性检查和机械臂可达性验证。

## 6. 现有代码怎么接进来

- robot.py：提取为 fairino 兼容适配器，集中处理 RPC、单位转换、状态读取、停止与错误。保留旧 /move_arm 作为过渡，不让新技能直接依赖旧消息字段命名。
- grap.py：提取为串口夹爪适配器，补协议响应校验、超时和状态语义。现有 get_grap_loc 不能直接等同“确认抓到物体”。
- utils.py：拆成 hsv_detector、visual_alignment、arm_motion_facade、gripper_facade、profiles；去掉与主 HTTP 服务的循环导入和共享全局状态。
- Arm1_server_M1_for_log.py：将 /grab、/loosen 的业务迁为 pick/place 技能；去程和回程拐点迁入 station profile。上层接口只接收并查询任务，运动由执行器串行执行。
- Constants.py、inflection_point.py：整合工位命名、预抓位、预放位、进入/退出路径、运输位，统一成带单位、坐标系和版本的配置。不同机械臂必须重新示教与验证，不能复用工业臂坐标值。
- woosh_demo.py：提取 task_group、wait_at_station、release_wait；等待增加截止时间和错误返回。
- WooshWebSocketClient.py：按实际协议逐项核验后接为可选底盘适配器。封装存在不等于已联调；例如 robot_go_to 中引用未定义 target，不能直接当作通用导航入口。
- Arm1_Dataset_semantic.py、采集目录：拆出 recorder，采集不再调用会开夹爪的 all_init。记录 ROS 数据与 task_id，硬件初始化默认不动作。
- groundino_client.py：可选远程语义检测后端，设置超时和结构化结果；不能直接用于闭环抓取，仍需三维定位和抓取规划。
- BakeUp/、modify、bake：只保留参考；新运行路径明确一套配置和模块，避免误导入。

需要先修复的集成问题：请求中的 test 当前不生效；抓放会覆盖 speed 为 100；响应缺乏真实完成验证；wait_done 忙等且无截止时间；主服务缺少完整任务互斥；初始化会打开夹爪。相机深度读取、SDK返回码、停止接口及并发行为也需单独验收。

## 7. 软件与部署建议

新平台建议以 Ubuntu 24.04 + ROS 2 Jazzy 作为保守基线，先确认待购驱动、相机、规划组件能使用同一发行版再锁定。Jazzy 的目标平台包括 Ubuntu 24.04 的 amd64 和 arm64，支持期到 2029 年 5 月；这不是要求现有 ROS Noetic 工程直接升级。[ROS REP-2000](https://raw.githubusercontent.com/ros-infrastructure/rep/master/rep-2000.rst)

底盘导航使用 Nav2；机械臂在具备可靠模型、关节状态和轨迹控制后接 MoveIt 2；自建差速底盘可接 ros2_control。MoveIt 的 PlanningScene 用于模型中的碰撞和约束检查，真实效果依赖模型和场景是否完整。[Nav2 官方仓库](https://github.com/ros-navigation/navigation2)、[MoveIt PlanningScene](https://moveit.picknik.ai/humble/doc/examples/planning_scene/planning_scene_tutorial.html)

原 SDK .so 为 Linux x86-64，部分还绑定 CPython 3.8，不可直接复制到 ARM 主板或新版 Python。过渡期让它们留在原有 Ubuntu 20.04/Noetic 设备进程中，通过显式版本化网关与新系统通信。网关需要状态、错误、取消和超时契约，不只转发旧 HTTP 的成功响应。优先接一台设备完成纵向验证，再扩展其他后端。

自建版本优先选择开源协议或提供匹配系统/架构驱动的部件，避免依赖这批旧二进制。开发电脑运行界面、编辑和离线分析；实体机器人上的 Linux 主机运行感知、任务与规划；控制板执行编码器采样、轮速闭环和看门狗。停止能力不依赖 Wi-Fi 或远端电脑。

建议目录（拟建，不是本次已实现）：

```text
robot_platform/
  interfaces/           消息、Action、错误与能力描述
  task_executor/        状态机、任务存储、资源与模式仲裁
  skills/               navigate / dock / observe / pick / place / stow
  perception/           颜色检测、RGB-D定位、语义检测插件
  motion/               机械臂规划、导航、视觉对位
  adapters/             fairino / woosh / serial_gripper / diy_base / diy_arm
  safety/               互锁、状态有效性、停止升级
  robot_description/    URDF/Xacro、碰撞模型、惯性参数
  profiles/             每台机器人的配置、工位与标定
  bringup/              启动、依赖就绪与生命周期
  api/                  HTTP任务接口与控制台
  recording/            关键帧、任务日志、回放
  simulation/           假驱动、传感器回放、物理仿真配置
}
```

## 8. 小机器人实体怎么搭

建议形态：两轮差速底盘＋稳定支撑轮、低位电池、刚性上层板、小型机械臂、平行夹爪、腕部 RGB-D、车载托盘。机械臂尽量靠近支撑区域中心，同时给前方留出抓取空间。导航激光雷达与腕部相机职责不同，要避免机械臂或托盘挡住传感器。

机械臂先按约 25–35 cm 级工作半径评估，需要有真实关节位置反馈、限位/零位方案、速度控制和可实现的停止机制。便宜的开环舵机套件可用于原理学习，但如果无法确认位置、停止和持物状态，不能给它承诺同等级的自主搬运能力。

底盘至少有编码器、闭环轮速控制、可靠停止、看门狗；导航版增加 2D 雷达与 IMU。RGB-D最小测距、视野、USB带宽和Linux/ARM支持，需按实际抓取距离核验。主机可选 x86 小电脑或 ARM 主板，以选定相机与驱动的兼容性为先；首版颜色识别不强制 GPU。

供电设计分别核算电机峰值、舵机堵转峰值、计算与相机负载，设置合适的保护与稳压。急停设计应考虑带载机械臂的制动/保持与防坠，不能简单承诺“全机断电就一定安全”。

稳定性不能只看静态底盘承重：要用机械臂最远伸出、带载、转弯、制动等最不利情况评估重心与倾覆力矩。首版限制工作区域、速度和加速度，运输时收拢；台面高度不匹配就先改工位或机械结构，不能只改坐标。

采购前必须索取：通讯协议/驱动、关节反馈示例、URDF或尺寸、可用工作空间、负载与臂展条件、供电要求、停止行为。先确定“抓什么、从多高抓、放多远”，再定型号和预算。本设计不提供未经核验的型号与报价。

## 9. 按验收门槛逐步搭建

### 阶段 A：无设备跑任务

实现接口、假驱动、状态机、日志和 profile。假驱动可注入掉线、超时、未发现目标、抓取失败与取消。验收：所有故障有明确终态，不发生同时抢占底盘/机械臂，不把接收成功当作完成。假驱动不证明物理可行性。

### 阶段 B：机械臂固定抓取

机械臂固定在台面；只抓指定区域内的单物体。完成标定、坐标转换、停止验证和抓取验证。建议用固定工况的 20 次测试做初步验收，至少 18 次完成且每次失败都有正确检测、记录与受控停止；这是进入下一阶段的试验门槛，不是最终可靠性承诺。

### 阶段 C：底盘独立导航

机械臂固定在运输位或先不装。验证遥控、里程计、定位、导航、停车、失联自动停止、障碍物停车。记录不同接近角度的停车误差；阈值应来自机械臂可达空间与抓取误差预算，而不是拍脑袋写死。

### 阶段 D：装车后停稳抓取

完成安装外参、整机模型和稳定性验证。底盘视觉对位后抓取，抓取时底盘不接受移动指令。验收覆盖对位失败、深度无效、物体不可达、相机断流、机械臂未收拢等场景。

### 阶段 E：完整搬运

把取物—托盘固定—运输—重新取物—投放贯通，做重复试验和故障注入。逐项记录导航、对位、抓取和投放成功率、任务用时、失败原因。再决定是否增加多物体、语义指令、自动充电或更多工位。

## 10. 最先做的一个纵向切片

新建独立平台目录，不改原提取包。先实现一个 pick_and_deliver 任务、一组 Base/Arm/Gripper/Camera 接口、一套假驱动与一个机器人 profile。用同一任务分别选择 mock、legacy、diy 后端；只有实际接通的能力显示为可用。

第一份实物演示应足够具体：同一房间两个低台、一枚红色小方块、固定取放区域、车载托盘。先完成这个闭环，就能验证你后续自己搭一台小机器人所需的大部分基础链路。

待你评审的关键选择：首版物体和台面高度、可接受整机大小、已有零件、预算范围。确认这些后才能给出有依据的 BOM、机械布局和采购清单。
