# PickGo Lab：2026-10-19 研究与实操计划

制定日期：2026-10-18。本文是下一次开发与实验计划，不代表以下新增功能已经实现，也不安排后台定时执行。

## 明天的目标

用现有相机完成一个可以重复验证的小实验：把红、蓝、黄色物体放进画面，得到对应送检帧的颜色、矩形框、中心和像素偏差；移走物体后清空结果。先测清楚什么条件下可靠，再增加稳定判断。

如果核心实验顺利，再实现“实物颜色选择虚拟搬运任务”：看到蓝色实物 → 显示蓝色任务预览 → 用户确认 → 仿真机器人搬运虚拟蓝色方块。这里只用颜色选择任务，实物位置不会自动成为仿真或真实机器人的抓取坐标。

## 已有条件与能力边界

- 相机：此前本机枚举确认内置 USB2.0 HD UVC WebCam，以及新接的 Intel RealSense D435 RGB / Depth 两个接口。明天开始前重新确认连接状态。本计划使用 RGB 接口，不启用深度流。
- 软件：轻量运动学仿真、Python 动作函数、本机服务、MCP stdio 和原 HSV 颜色识别适配已经具备。
- 已实测：D435 RGB 曾采集 640×480 彩色画面并送入原检测器，当时返回未匹配目标。这只证明采集与送检链路连通；真实红蓝黄识别尚待验收。
- 当前坐标：识别结果对应 320×240 送检图，中心与偏差单位是像素；矩形角度不是机械臂关节角。当前不输出真实距离、物体三维位姿或模型置信度。
- 当前自动搬运：使用虚拟场景的几何位置，不是视觉闭环。现有摄像头结果尚未连接搬运入口。
- 实体执行：本次记录没有确认可用的实体机械臂和底盘，因此明天的执行效果以仿真为终点。
- 深度：按此前决定继续暂缓。Astra Pro SC 的旧原型也不列入明天必做项。

## 准备材料与工作方式

准备红、蓝、黄色的哑光纸片、积木或盒子各一个，浅色背景纸、固定相机的支架或稳固垫台，以及用于标记位置的胶带。尽量使用形状清楚、面积足够的目标，不需要购买新设备。

相机先固定，关闭其他占用相机的软件。选一台相机作为主实验设备，优先沿用已经连通的 D435 RGB；内置相机用于故障回退和后续对比。每次实验记录设备、光照、背景、目标颜色、位置和放大倍数。

你负责摆放目标、调整环境和确认实际颜色；代码开发与统计围绕这些实测记录进行。先用均匀光照和简单背景建立基线，不能同时改变背景、距离、缩放和阈值后再归因。

## 核心阶段一：复核环境与建立基线（约 30–45 分钟）

1. 在本项目目录运行 `python -B app.py --vision-only`，打开终端显示的 localhost 地址，再进入 `/vision.html?source=camera`。该模式不启动仿真。
2. 先用合成图确认红、蓝、黄检测可用，再明确选择 RGB 接口，手动打开相机。
3. 在均匀光照、浅色背景下逐个放入目标，分别选择对应颜色，使用单帧送检。
4. 固定放大倍数，调整物体大小或距离，让目标有足够画面占比。原算法约有 4% 颜色占比门槛，并有轮廓尺寸限制，不能把很小的目标视为必然可识别。

产出：一套能复现的相机摆放、光照、背景、缩放配置，以及三种颜色的初次成功或失败记录。若某颜色识别失败，先记录条件，再进入阈值排查，不把合成图成功记作实物成功。

## 核心阶段二：做一个小型识别实验（约 60–90 分钟）

研究问题：同一颜色移动到画面不同位置后，能否稳定识别？失败主要来自目标占比、反光、背景还是原 HSV 阈值？

实验使用固定的主相机、缩放、背景与光照：

- 3 种颜色 × 左 / 中 / 右 3 个位置 × 每位置 5 次独立摆放，共 45 次正样本。目标需完整留在送检区域。
- 再移走目标，做 10 次背景样本；摆放间适当停顿或重新移动物体，不把连续相邻帧当作独立实验。
- 可追加 5 次遮挡、反光或变暗试验，单独记录，不混入上述基线成绩。

每次至少记录：编号、相机、目标颜色、位置、光照、缩放、是否找到、返回颜色、中心、像素偏差、算法耗时、端到端耗时与备注。未识别、背景误报、颜色错误分别计数；耗时尚未采集时留空，不能用算法内部耗时代替端到端耗时。

建议验收目标是 45 次中至少 41 次正确识别，并单列每种颜色、每个位置的成绩；10 次背景样本不应报告目标。它们只是本次固定场景的工程门槛，样本量不足以证明通用识别率或零误报。如果未达标，交付失败分布与原因，比调整条件后只展示一次成功更有价值。

默认只保存文字或 CSV 统计，不保存相机画面。确需留图时再由用户主动选择要保留的样例。

## 核心阶段三：围绕失败点改进稳定性（约 90–120 分钟）

下列为待开发项，先完成最影响实验的部分：

1. **可解释排查。** 增加 HSV 掩膜与目标颜色占比显示，帮助区分“颜色没进入阈值”和“进入阈值但轮廓不满足条件”。当前通用 NO_MATCH 不能直接当作具体失败原因。
2. **独立配置。** 如确需调整 HSV，保留原配置与 `legacy/utils.py` 不变，在新适配层增加明确命名的相机实验配置；记录修改项，并重新跑同一组实验，比较前后结果。调整与验证尽量使用不同摆放轮次。
3. **稳定目标状态。** 同色目标连续 3 次有效且中心变化在预设容差内，才标为“稳定”。初始容差可试 10 像素，再由实测决定。移动或遮挡时显示“不稳定 / 未检测”，不沿用旧坐标。这里的稳定状态不是概率置信度。

额外检查：固定一个目标采集 20 次结果，统计识别次数与中心波动；移走、遮挡、切换颜色各做一次，确认旧框和坐标会清空。

原检测函数有 0.4 秒等待，连续模式还要等待请求返回，所以预览流畅不代表检测达到视频帧率。明天记录实际响应时间，稳定判断需要的等待也以实测为准，不承诺高帧率。

## 拓展阶段：实物颜色联动虚拟任务（核心达标后，约 60–90 分钟）

待实现流程：稳定识别一个颜色 → 生成可见任务预览 → 用户确认 → 调用已有 `grab_and_send` → 查询并显示同一 `task_id` 的运行结果。

需要以完整 `app.py` 启动共享仿真；`--vision-only` 不提供运动仿真。直接入口先用已有 Python / 本机服务，MCP 沿用同一业务函数。

最低验收：

- 红、蓝、黄各完成一次“识别 → 确认 → 虚拟搬运”。
- 目标一直留在镜头里也只生成一次待确认任务，不逐帧重复搬运。
- 无目标、结果过期、相机断开时不能确认旧结果；任务已运行时不另启搬运。
- 暂停、继续、停止沿用现有任务控制，并核对任务结果。

此演示可以准确描述为“视觉识别选择仿真任务”，不能描述为真实视觉抓取或视觉导航。

若前面有余量，再增加只读 `get_latest_observation` MCP 工具，返回来源、帧标识、采集时间、识别结果与新鲜度。当前没有这个工具，也没有 MCP 实时视频流。观测过期或来源变化时明确失效；动作仍走独立确认与已有搬运入口，不让读观测自动触发动作。

## 明天重点研究的创新点

1. **相机观测成为独立能力。** 把“看到什么”与“执行什么”分开，后续网页、Python、MCP 复用同一观测格式。这比把相机直接绑进单个抓取函数更方便替换算法和设备。
2. **稳定性有证据。** 配置、实验条件、误报漏报和时延可以复现，让项目从展示一次成功发展为能比较不同方案的小实验平台。
3. **真实输入驱动虚拟任务。** 先打通低成本的颜色决策闭环；未来增加标定、深度、规划和硬件驱动时，每一步都有可独立验收的入口。

明天先研究并验证第 1、2 项，完成核心后再实现第 3 项。第二台相机的同条件对比、固定平面坐标标定、D435 深度、通用物体检测与实体抓取均不同时展开。

- 关闭摄像头、释放设备。源码与小型记录留在当前轻量项目，不打包 Python 环境、SDK、录屏或下载目录。

核心阶段加收尾预计约 3.5–5 小时；联动另留约 1–1.5 小时。时间是工作量估计，识别未达标时优先排查与记录，不为赶联动而跳过验收。

最低成果：一套已验证条件下的 RGB 识别基线、一份小样本统计、明确的失败原因与下一步改进。理想成果：在此基础上得到稳定状态，并完成三种实物颜色对虚拟搬运任务的选择与确认。

## 深度恢复时再做什么

以后若决定恢复 D435 深度，单独安排 SDK 接入、彩色与深度时间对应、深度到彩色配准、有效深度过滤和坐标标定。官方 SDK 提供 [彩色与深度对齐示例](https://github.com/realsenseai/librealsense/blob/master/wrappers/python/examples/align-depth2color.py)。不能把浏览器 RGB 与任意另一时刻的深度图直接拼成测距结果，也不能用缩放图像代替配准。

该方向不属于明天的必做项；本次只制定计划，没有安装 SDK、打开相机或修改运行代码。
